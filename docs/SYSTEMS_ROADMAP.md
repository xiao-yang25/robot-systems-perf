# 具身/机器人机器接入、业务观测与优化路线

本文定义下一步产品设计与交付边界，生产代码尚未实现的能力明确标注。当前运行入口见 [README](../README.md)，现有模块和数据口径见 [架构设计](ARCHITECTURE.md)。

## 产品目标

每一台新机器接入后，先读取平台基本信息并按可用能力建立基线，再结合现场业务配置观察功能节点的中间件与系统行为。相同工具、指标定义与报告在不同机器复用；平台差异由能力检测和平台适配处理，业务差异由显式业务档案处理。Orin/Thor 是优先验证的平台；其他 Linux 机器人计算平台属于后续适配目标，不能因能够启动就声明已支持。

第一阶段交付机器接入与测量工具。第二阶段按中间件与系统两个领域维护优化实验和方法；其验收共用第一阶段工具。方法库持续扩展，有限版本不以穷尽所有优化方法为完成条件。

仓库拆分有两种可行落点，待使用者明确：第一阶段保留 `robot-systems-perf`，第二阶段分为 `robot-middleware-optimization` 与 `robot-system-optimization`（名称为提案，总计三个仓库）；或者第二阶段合并为一个优化仓库，内部分两个领域（总计两个仓库）。本设计不创建新仓库、不搬迁当前源码。领域和数据交接规则不依赖这项命名决定。

## 第一阶段：新机器接入到可解释报告

| 顺序 | 输入与处理 | 交付物与边界 |
| --- | --- | --- |
| 1 平台盘点 | 只读识别硬件、系统/BSP/内核、部署、可用资源接口及工具；软件和人工条件逐项注明来源 | 平台档案、能力清单、工具实际可运行性；功耗模式和传感器值按实际读取，不预设相同平台接口 |
| 2 业务建档 | 现场声明功能角色、进程/服务范围、ROS domain/节点、组件、topic、输入输出与期望频率 | 业务档案与目标清单；候选发现与算法身份分开 |
| 3 关联对象 | 按范围注册进程身份，再关联节点、组件、回调与线程；保存关系来源和有效窗口 | 多对多对象关系；配置声明、追踪观测和推测分开，未知关系保留未知 |
| 4 选择测量 | 轻量资源观察为起点；按问题追加周期/通信基准、ROS事件或CPU/GPU/内核追踪 | 有界测试计划，权限/依赖/开销预检；生产业务默认只读，回放/注入是明确选择的隔离实验 |
| 5 保存证据 | 时间戳、配置、版本、原始记录、源窗口、对象身份、覆盖和缺失原因 | 独立结果目录；现有schema继续兼容，新增关联采用单独带版本记录，不先重写所有输出 |
| 6 分析与交接 | 资源与业务事件按有效身份、时钟和窗口关联；各自检查输入、交付、覆盖、deadline及采集预算 | 机器基线、业务观测报告、异常片段与证据缺口；未配置要求不判通过 |

“基本信息”以静态/配置档案为主；动态性能由独立基准和业务观测获得，不能只根据型号/频率推断。先做单机；跨机器、传感器时间戳与GPU时间线关联必须声明时钟域、转换方法和误差，未对齐时不相减。

### 功能节点与进程的关联

该关联是当前下一项主要缺口。一个进程可能承载多个组件/节点，一个节点可能使用多个线程；线程池也可能执行多个回调。进程CPU/RSS不直接等于某个节点的独占资源，节点图发现也不证明PID对应关系。

最小业务档案应包含功能角色、业务版本、UID/PID/名称/cgroup范围、节点与组件标识、相关topic/type/QoS、选定输入输出边界和关联方式、期望频率及选填deadline。敏感名称和部署路径只保存在现场。优先接受人工配置和已有launch/部署信息；能用trace元数据核对时增加观测证据。名称相似仅为候选线索，不自动升级为确认关系。

关联身份至少保留主机/运行标识、PID及启动身份、节点/回调标识、来源与有效时间。重启后建立新关系，不把旧回调、计数或消息连接到复用PID。对于无法关联的对象，仍可输出进程资源，节点归属标为不可评估。

### 业务测量分层

| 层次 | 指标与证据 | 前提 |
| --- | --- | --- |
| 系统/进程 | CPU、RSS、缺页、切换、cgroup节流、可用累计调度等待、GPU/EMC等整机指标 | 只读接口及有效身份；采样遗漏与字段缺失单列 |
| 节点/回调 | 回调墙钟时间、频率、可观测通信阶段和事件覆盖 | 兼容ROS tracepoints与对象关系；CPU时间需要额外调度/线程证据，不能只用callback墙钟估算 |
| 业务路径 | 输入到输出延迟、数据年龄、吞吐、未完成及deadline | 明确业务边界、稳定关联ID或经验证的关联规则；同步、多输入/多输出关系明确 |
| 因果诊断 | runnable/off-CPU、IRQ、执行器、DDS或GPU同步等异常原因 | 对应事件/工具与时钟关联，资源相关性不能替代因果证据 |

无需为每个算法重写基础采样；实际业务只补范围、路径、关联与验收要求。无法无侵入关联时，按应用选择最小埋点或受控输入输出监测，标出增加的扰动。

## 工具复用与适配原则

项目主要负责预检、计划执行、生命周期、配置、证据关联、分析和报告；专业追踪由成熟工具提供，基础采样不强制安装全部外部工具。用少量具体CLI适配或离线结果导入，暂不建立通用动态插件框架。

| 需要回答的问题 | 优先复用的工具/已有能力 | 接入边界 |
| --- | --- | --- |
| 基础资源及采集成本 | 现有monitor、sysstat/pidstat、Jetson tegrastats | 前两项对照与可选Jetson遥测已有基础；整机指标不自动分摊到节点 |
| 周期唤醒与参考通信 | 现有S01/C01、cyclictest | 已有入口，需实际worker条件、样本资格与工具选项/权限核验 |
| ROS回调和事件 | ros2_tracing/LTTng，必要时tracetools_analysis或CARET | 当前入口验证事件可采；节点归属、路径分析和兼容SDK尚需接入与设备验证 |
| 固定业务图输入输出 | NVIDIA ros2_benchmark | 规划接入；需现场配置测试图、输入/输出监测和匹配的ROS环境，不自动替业务设允许丢失比例 |
| 内核实时性原因 | perf、RTLA，按需BCC/eBPF | 规划接入；按目标内核/权限支持选择，不能假设每台Jetson都可用 |
| CPU/GPU协同与同步 | Nsight Systems | 规划接入；按JetPack选Embedded Platforms版本，短诊断窗口并检查开销/事件覆盖 |

官方依据： [ros2_tracing](https://github.com/ros2/ros2_tracing) 描述ROS核心事件、LTTng及发行版分支；[ros2_benchmark](https://github.com/NVIDIA-ISAAC-ROS/ros2_benchmark) 描述测试图的输入播放、输出监测及实时输入模式；[RTLA](https://www.kernel.org/doc/html/latest/tools/rtla/rtla.html) 提供timerlat/osnoise等内核实时性分析；[Nsight安装指南](https://docs.nvidia.com/nsight-systems/InstallationGuide/index.html) 要求Tegra选择对应JetPack的Embedded Platforms版。资料于2026-10-05核对，仍以设备上选定版本的预检与实跑为准；不因此改变当前依赖或声明全部工具已适配。

## 第二阶段：可复用的优化实验与方法

中间件领域覆盖RMW/DDS、QoS与队列、消息/序列化/复制、进程内/跨进程通信、共享内存、executor/callback group以及发布/接收线程布局。系统领域覆盖调度与亲和性、CPU/IRQ隔离、内存与缺页、锁与竞争、I/O、容器配额以及CPU/GPU协同。这里只定义方法分类，不宣称某项手段对所有场景都更好。

一个方法条目必须有：问题与适用条件、应看到的瓶颈证据、机制说明、最小复现、确切修改、恢复方法、第一阶段测量计划、正确性/交付/期限/资源验收、实际结果与适用版本、负面结果或未知项。未经实测的条目标为候选，单台有效不写成普适收益。

优化仓库按明确选择运行实验，涉及系统设置或业务部署的修改应先输出可审阅方案，再在授权实验环境执行并保留恢复证据；不把一套调优参数自动应用到每台新机器。

### 仓库之间的交接

第一阶段工具是测量与结果口径的维护位置；优化领域复用它的确定版本与测试计划，不复制采样/统计实现、不维护第二套指标定义。每个实验关联测量工具版本、平台档案、业务版本、输入负载、基线/修改配置、运行顺序、原始结果目录与分项验收。

中间件与系统边界有交叉，例如executor线程绑定、共享内存和GPU数据通路。按主要修改对象指定一个实验归属，引用另一领域的前提或方法；联动实验分步改变变量，避免两个仓库重复维护同一案例。结果与原始数据留设备或受控存储，公开仓库保存可复现代码、通用模板和脱敏结论。

## M1/M2 首批实施设计

M1 已实现 `robot-perf-intake`，M2a 已实现 `robot-perf-monitor --workload`。用户反馈 0.6.0 在三台 Orin/Thor 上安装集成与机器信息回归通过，Orin 完成真实进程资源关联；节点语义仍为声明。0.6.1 参数读取顺序、纯PID路径和异常收尾已收到三机通过的现场反馈；纯PID四轮对照支持该配置的采集成本下降，不证明业务扰动改善。0.6.2 最终状态保存时中断叠加摘要/报告错误的有限修补已收到三机通过反馈并收尾，见 [机器接入指南](MACHINE_INTAKE.md) 与 [业务功能关系指南](BUSINESS_MAPPING.md)。0.7.0实现M2b首批独立图查询与规范化初始化元数据导入；原生CTF与真实追踪SDK/身份实证仍待适配，见 [M2b指南](ROS_BUSINESS_EVIDENCE.md)。两项均扩展当前测量仓库，暂不依赖第二阶段仓库的数量决定。

### M1：新机器接入包

**使用流程**：在目标宿主运行只读接入，获得机器档案和能力报告；填写自动读取不到的部署/散热条件；检查建议采集配置；再明确选择是否执行已有S01/C01或短资源观察。接入本身不自动启动基准、安装依赖或改变系统设置。

复用 `platform_probe.collect_profile` 与现有配置验证；新增 `perfkit.intake` 和可安装入口，输出下列文件。工具版本/采样资格由显式调用既有工具对照入口验证，M1 不启动外部命令：

| 文件（M1 已实现） | 内容与来源 |
| --- | --- |
| machine-profile.json | 操作者提供的非敏感机器代号、运行ID、工具版本、当前可见平台与操作者声明的视图及来源；软件/人工字段带来源与读取窗口，不把操作者填写当成已读到 |
| capabilities.json | proc/sysfs等逐项读取状态；工具发现、版本/选项检查及实际采样验证分别记录，未执行的验证保持未验证 |
| MACHINE_REPORT.md | 设备摘要、可采指标、限制和具体下一步；只对明确要求的能力给可用/不可用判断 |
| monitor-config.suggested.json | 基于已有light配置生成，通过现有monitor验证；不预设算法名称、业务deadline或CPU预算，现场选择范围后使用 |
| intake-status.json | 接入执行状态、必需项失败、可选项缺失和已完成步骤；采集完成与目标平台支持分开 |

先保持旧environment/资源输出不变，新接入包用自己的版本字段关联，避免重写所有既有schema。机器代号由使用者提供或本地生成匿名代号；不从序列号/主机名构造公开身份，不因系统升级覆盖旧档案。视图通过 `--view` 声明，默认 unknown，不作自动宿主认证；当前没有宿主档案导入功能，不能用容器探测冒充宿主信息。

M1 将工具发现、版本/选项与采样状态分开；后两项不查询、不判 ready，找到工具仍保持未验证。实际 trace/基准资格由独立显式执行的工具对照结果提供；当前不导入对照结果到接入档案，不新增全局探测器。

**M1验证与结束条件**：

- 已知Orin、Thor和非Jetson Linux测试数据得到正确平台/能力来源；非目标平台按显式要求拒绝或降级，不猜型号/BSP兼容。
- 缺ROS、缺外部工具、权限不足、缺sysfs时仍保留有原因的结果；明确必需项缺失则退出非零，不能总报成功。
- 新目录正常输出；已有目录拒绝覆盖，失败保留状态；安装后从任意目录运行。
- 建议配置通过现有monitor验证且预算保持null；不默认绑定CPU或开启高成本线程/trace。
- 本地Linux验证入口与输出后，在Orin/Thor各做一次只读接入复核；不因此重跑全部性能套件。需要新的平台性能基线时独立选择负载和固定轮次。

### M2a：业务清单与进程关系

先实现不依赖ROS tracing SDK的核心路径：载入现场业务清单 → 校验 → 复用现有发现/筛选 → 固定进程身份 → 保存关系 → 在资源报告里引用关系。业务清单独立于monitor配置，通过 `--workload` 传入；下述示例符合当前清单格式，需先替换现场规则。

```json
{
  "format_version": 1,
  "workload_id": "robot-demo",
  "functions": [
    {
      "id": "perception",
      "process_selector": {"include_names": ["^demo_container$"]},
      "ros_nodes": ["/demo/detector", "/demo/tracker"],
      "relation_source": "operator_declared"
    },
    {
      "id": "control",
      "process_selector": {"include_names": ["^demo_control$"]},
      "ros_nodes": ["/demo/control"],
      "relation_source": "operator_declared"
    }
  ]
}
```

UID、硬cgroup范围、排除项与节点/domain等字段在实现契约中明确校验；仅按名称选到的对象仍是候选。每项选择器单独验证，不能简单合并成全局规则后扩大范围或改变并集/硬过滤语义。既有配置若不能表达业务范围，明确拒绝或在原筛选之上核对关系，不静默放宽。功能字段仅作资源报告归类，不因填写角色就证明算法类型。

新增关系记录至少包含业务版本、功能ID、PID/starttime、采集命名空间、节点名/标识、来源、有效窗口与状态。操作者声明关系与进程身份已核对是两个独立事实；图中节点存在也不能将声明升级为PID归属已验证。零匹配保留unresolved；超出声明基数、同名冲突或证据矛盾保留ambiguous/conflict，不选第一个候选冒充确认。

注册/注销沿用当前monitor的身份变化事件；业务关系随着旧进程身份失效，不跨PID重用延续。每个进程只有一份CPU/RSS记录，多个节点或功能引用它；组件报告显示共享进程资源，不将相同CPU重复求和，也不按节点数均分。无法归属的线程保留进程级观察。

已实现输出为workload-profile.json、business-relations.jsonl和BUSINESS_MAP_REPORT.md，原resources.jsonl和monitor-summary.json继续兼容，后者增加workload引用。报告区分候选、未匹配、数量不足、歧义和声明冲突；所有节点仍是人工声明，尚无追踪验证。报告按功能查整段资源注册指标，不按关系子窗口重新统计，也不产生未采到的回调耗时或业务路径时延。

### M2b：ROS图与可选追踪证据

ROS图采集作为明确启用的有限快照：节点/namespace、topic/type、endpoint QoS，以及组件管理器可报告的组件关系。查询采用对应发行版的CLI或ROS环境内小型适配器，基础Python采样器继续仅依赖标准库；不默认订阅业务数据、启动全局daemon、修改参数或加载/卸载组件。图快照来自指定domain和发现范围，可包含其他机器节点，不能默认全部属于本机。

官方Humble [节点列表实现](https://github.com/ros2/ros2cli/blob/humble/ros2node/ros2node/verb/list.py) 使用图节点名称，并提示重复名称；[组件list接口](https://docs.ros.org/en/humble/p/ros2component/ros2component.verb.list.html) 列出运行容器与组件。以实际CLI输出/超时为证据，图为空、权限/网络失败、重复名称和不可观测组件分别报告，不把空输出解释成没有业务。

能取得兼容trace时，用节点/发布订阅/回调初始化元数据及记录来源补充关系。[Humble tracepoint定义](https://github.com/ros2/ros2_tracing/blob/humble/tracetools/include/tracetools/tracetools.h) 提供node handle、名称/namespace及发布订阅关联。适配器还必须核对事件上下文PID的命名空间、运行身份和时间域；仅一个名字或裸PID不足以合并。

首批不为采初始化元数据重启现有业务。缺初始元数据、无法对齐身份或tracepoints未编译时保留配置声明/未知；trace格式和工具版本未经支持的导入应失败。回调CPU归属、消息端到端路径和deadline统计属于M3，M2只交付可核对的对象关系与现有资源引用。

**M2验证与结束条件**：

- 两个代表部署：一个独立节点进程；一个承载两个节点的组件容器。首批允许操作者声明关系，追踪验证与声明明确区分。
- 相同进程被两个节点/功能引用时，资源不复制求和；进程重启/PID重用后旧关系失效，新身份独立记录。
- 节点存在但没有本地PID证据、重复节点名、名称规则匹配多个对象、目标消失和不可读均有明确状态；不能误称确认或无业务。
- 无ROS/无tracing环境下M2a仍可观察资源并保存声明，M2b标不可用；图查询原始证据及实际窗口保留。

- 本地受控部署通过后，在设备选择一套现有业务做有限关系复核。现场只需在本地填业务代号、范围与节点清单，原始配置不进入公开仓库。
